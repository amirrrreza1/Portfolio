# Internationalization specification

Normative decision: [ADR-005](DECISIONS.md#adr-005--bilingual-articles-as-per-locale-translations-of-one-post).

## 1. Locales

| Locale | Language | Script direction | Fixed site UI font | Role             |
| ------ | -------- | ---------------- | ------------------ | ---------------- |
| `en`   | English  | `ltr`            | JetBrains Mono     | Default locale   |
| `fa`   | Persian  | `rtl`            | Vazir Code         | Secondary locale |

The locale set is a closed allowlist in code. These fixed UI fonts keep navigation and non-blog pages locale-appropriate; the visitor-selectable blog font is a separate preference. Adding a locale is a code change plus a font and typography review, never a database row that appears untested.

Three separately configurable things are often conflated and MUST NOT be:

- **UI locale** — the language of navigation, labels, and buttons.
- **Content locale** — the language of the article or portfolio text being read.
- **Appearance preferences** — site-wide theme and blog-only typography, covered in [THEMING.md](THEMING.md).

## 2. Routing

All public routes are locale-prefixed, including the default locale:

```text
/en                      /fa
/en/projects             /fa/projects
/en/blog                 /fa/blog
/en/blog/<slug>          /fa/blog/<fa-slug>
/en/blog/category/<slug> /fa/blog/category/<slug>
/en/blog/tag/<slug>      /fa/blog/tag/<slug>
```

Rules:

- No unprefixed public content URL exists. `/` and any legacy unprefixed path issue a `308` to the resolved locale. A visible prefix everywhere means one URL shape, one canonical form, and no ambiguity for crawlers. **Partly implemented:** `/` issues its `308`, but the legacy unprefixed paths do not redirect yet.
- Locale detection for the bare `/` request only: cookie preference, then `Accept-Language` negotiation against the allowlist, then default `en`. Detection MUST NOT redirect a request that already carries an explicit locale prefix, and MUST NOT prevent a crawler or a reader from reaching either version. **Outstanding:** middleware currently sends every `/` request to `/en` with no negotiation, so a Persian-preferring visitor lands on English.
- An invalid locale segment is a `404`, not a silent coercion to the default.
- The admin panel is not locale-prefixed. It is English-only in this release, and that is a stated scope decision rather than an omission.
- Locale is resolved once in middleware and passed down; components never re-detect it.

## 3. Article translations

One `Post`, one `PostTranslation` per locale, per [DATA_MODEL.md](DATA_MODEL.md) §5.

- Each translation owns its own title, slug, excerpt, SEO fields, body file, status, and `publishedAt`.
- Shared across translations: category, tags, cover image, and the post identity.
- Status is per translation. English can be published while Persian is still a draft.
- **No fallback.** Requesting `/fa/blog/<slug>` for a post with no published Persian translation returns `404` with a helpful page that links to the English version. It does not render English text under a Persian URL.
- The language switcher on an article offers only locales with a published translation of that post. When the other locale does not exist, the control is absent, not disabled with a dead-end.
- Switching language from a listing or portfolio page goes to the equivalent page in the target locale, not to the home page.
- Slug histories are per locale. Renaming the Persian slug creates a redirect only within `/fa`.

## 4. Portfolio and UI text

- **UI strings** live in versioned message catalogs in the web app (`en.json`, `fa.json`), typed so a missing key is a build error rather than a runtime blank. Interpolation is escaped; no catalog value is ever treated as HTML. **Not started:** the catalogs do not exist, and every UI string in the components is still an English literal, so `/fa` currently renders English chrome with Persian direction.
- **Portfolio content fields** are translatable, with English required and Persian optional. Unlike articles, portfolio fields **do** fall back to English when the Persian value is absent, because a portfolio page with a missing skill-category label is broken in a way a missing article is not. The fallback is visible in the admin panel as an untranslated-field indicator so gaps are apparent and closable.
- This asymmetry is deliberate: an article is a document a reader chose to read in a language; a portfolio page is a single page whose fields are independently authored.
- Every translatable field is enumerated in [CONTENT_INVENTORY.md](CONTENT_INVENTORY.md).

## 5. Document attributes and typography

- `<html lang>` and `<html dir>` are set from the resolved locale during server rendering. **Done in M4:** the hard-coded `lang="en"` is gone; the root layout resolves the locale from the middleware header and the locale layout emits the matching `lang`/`dir` on its subtree.
- A mixed-direction inline run (Latin code or a URL inside Persian prose) is wrapped so bidirectional reordering cannot mangle it. Use logical CSS properties (`margin-inline-start`, `padding-inline-end`, `text-align: start`) throughout; physical left/right properties are treated as a defect in shared components.
- Persian text uses locale-appropriate line height and letter spacing. Persian digits are a display concern: store numbers canonically, format at render time per locale.
- Dates are stored as UTC and formatted per locale with `Intl`. Persian pages use the Persian (Jalali) calendar for human-readable dates, while `datetime` attributes and structured data keep ISO 8601 Gregorian values, because machines read those.
- Code blocks stay `ltr` inside RTL documents.
- Persian articles need a Persian-capable font at the required weights. The existing `Vazir-Code` files cover this; any weight the design uses MUST actually exist as a file.

## 6. SEO for two locales

Extends [SEO.md](SEO.md).

- Each locale page is self-canonical. A Persian article never canonicalizes to the English one — they are different documents for different readers.
- Reciprocal `hreflang` links are emitted **only between translations that are both published**, plus `x-default` pointing at the English version. An unpublished or missing translation gets no `hreflang` entry, since a link to a `404` is worse than no link.
- `hreflang` values are `en` and `fa` with absolute URLs, present in both directions, and validated in CI.
- Open Graph `locale` is set per page, with `og:locale:alternate` only for an existing published translation.
- The sitemap lists each published translation as its own entry with `xhtml:link` alternates matching the emitted `hreflang` set exactly. Sitemap and page metadata are generated from the same source so they cannot disagree.
- One RSS feed per locale, each containing only that locale's published translations.
- Per-locale `BlogPosting` JSON-LD carries `inLanguage`, and its `headline`, `description`, and `datePublished` come from that translation, not from the post's other language.
- Automatic locale redirection MUST NOT be applied to prefixed URLs, so a crawler indexing `/fa/...` is never bounced to `/en/...`.

## 7. Configuration and API

- Public read endpoints take an explicit, validated `locale` parameter. There is no implicit server-side default that could silently serve the wrong language.
- Locale participates in the cache key for every public read and in cache-invalidation tags, so publishing a Persian translation does not purge English pages and vice versa.
- Admin endpoints address a translation explicitly (`/admin/blog/posts/:id/translations/:locale`) rather than inferring locale from a header.
- `Content-Language` is set on public responses. `Vary: Accept-Language` is set **only** on the bare `/` negotiation response, never on prefixed pages, so the cache is not fragmented across every browser language string.

## 8. Tests

- Prefixed routing: every public route resolves in both locales; unprefixed and invalid-locale paths behave as specified.
- Negotiation: cookie beats `Accept-Language`; an unsupported language falls back to `en`; a prefixed URL is never redirected.
- No-fallback guarantee: a post with only an English translation returns `404` for the Persian URL and English text never appears under a `/fa` article URL.
- Switcher: only published translations are offered; equivalent-page switching from listings and portfolio pages.
- `hreflang`: reciprocal and absolute for published pairs, absent for missing translations, `x-default` present, sitemap alternates identical to page metadata.
- Direction: `lang`/`dir` correct per locale; no physical-direction CSS leaks in shared components; bidirectional inline runs render intact; code blocks stay `ltr`.
- Catalogs: no missing or unused keys; catalog values are escaped, not interpreted as HTML.
- Caching: locale is in the cache key; publishing one locale does not invalidate the other.
- Portfolio fallback: a missing Persian field renders the English value and is flagged as untranslated in the admin panel.
