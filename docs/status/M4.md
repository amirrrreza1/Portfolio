# M4 — Public bilingual cutover

Status: **In progress**  
Snapshot: **2026-08-16**  
Depends on: M2 and M3; shell work was intentionally pulled forward  
Roadmap: [M4 definition and exit gate](../ROADMAP.md#m4--public-bilingual-cutover)

## Outcome so far

Five live-proven database-backed portfolio boundaries exist: project lists, project detail/optional images, the localized site shell and ordered page sections, appearance, and homepage collections/documents. The sixth public boundary, articles, is now implemented and automated-verification complete across strict contracts, published-only API reads, 15-minute bounded stale clients, route-level `503` handling, bilingual list/detail pages, no-fallback `404` behavior, current-render provenance, and published-only SEO metadata. Root locale negotiation, the active English/Persian UI catalogs, server-side cached allowlisted GitHub statistics, and localized HTTP `503` responses for the earlier routes remain production-proven. Explicit legacy rendering remains API-independent. The signed invalidation path is now implemented on both sides — the worker drains the outbox with bounded retries, and the web app verifies timestamp, nonce, body digest, and signature before purging. M4 stays open because the M3 content branch has not supplied a real indexed bilingual article, and because an implemented invalidation path is not a proven one.

- Signed, locale-scoped invalidation: the outbox row is written inside the apply transaction, the worker drains it with capped backoff and a visibility timeout, and the receiver verifies timestamp, nonce, body digest, and signature in constant time before purging.
- A live run drove the real drain and sender against a real `next dev` process over a real socket, with the outbox in real PostgreSQL: delivery, nine rejection cases, and retry-then-recovery all behaved as specified. See [`evidence/M4-invalidation-live.md`](evidence/M4-invalidation-live.md), which also records what the run does not prove.
- Listings register a collective cache tag alongside their per-page key. The live run found that they previously did not, so publishing an article purged its detail page and left every cached listing stale; `apps/web/test/invalidation-tags.spec.ts` now asserts the publisher's tags against the tags the reader actually registers.
- Cache tags are built by one shared function in `@portfolio/contracts/content` that both the web client and the API use, so a purge cannot miss because two processes spelled a tag differently.
- Invalidation clears both cache layers. `revalidateTag` alone would leave a withdrawn article being served from the in-process last-known-good buffer for the rest of its stale window.
- A signed request carrying a body that is not a valid event is refused, so holding the secret does not grant the ability to send arbitrary shapes into the purge path.
