# M9 — Operations, release, and cleanup

Status: **In progress**
Snapshot: **2026-09-05**
Depends on: M5, M8 — both complete

## Implemented

- Multi-stage non-root web, API, worker, and migration images; production-like Compose profiles; private data networks; health checks; read-only application filesystems; dropped capabilities; PID/CPU/memory limits; and a Caddy edge.
- A one-shot migration service that gates API startup, plus distinct publication, scheduler, and maintenance processes.
- Readiness now checks PostgreSQL, MinIO, and publication backlog without exposing credentials or dependency versions.
- Failed contact delivery records bounded attempts and retry timing. The maintenance worker retries with exponential backoff, leaves exhausted failures visible, and purges messages at their stored retention deadline.
- Owner-only contact listing, retry queueing, and deletion operations; dashboard counts for contact delivery, overdue retries, publication/invalidation state, and media storage.
- Expired import-report cleanup and conservative orphan cleanup for old archived or terminal media, with object-deletion failures retained for a later pass.
- Encrypted combined PostgreSQL/MinIO backup and guarded isolated-restore scripts, a content-integrity verifier, deployment/rollback, backup/restore, and incident runbooks, and a bilingual release smoke command.
- CI gates for migrations against PostgreSQL 17, generated OpenAPI drift, production dependency audit and license policy, hardened image builds, Trivy scans, and retained SPDX SBOMs.

The repository can prove schema generation/validation, typecheck, unit tests, build output, OpenAPI determinism, license policy, Compose rendering, and script syntax. Docker image execution and the full restore drill require a running Linux container engine and isolated PostgreSQL/MinIO targets.
