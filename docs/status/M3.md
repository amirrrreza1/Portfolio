# M3 — Git content-store proof

Status: **In progress**  
Snapshot: **2026-08-24**
Depends on: M1 and M2  
Roadmap: [M3 definition and exit gate](../ROADMAP.md#m3--git-content-store-proof)

## Outcome so far

The content-store package contains the core secure transport, reconciliation, and durable recovery primitives, and they are now wired into a running system: a PostgreSQL job queue, a dedicated worker process, an enqueue-only webhook endpoint, and readiness reporting that degrades instead of failing. A repository-scoped GitHub App is now authenticated against the real repository, and the real `content` branch contains a reconciled published English/Persian article. The remaining gate is owner-level protection/secret-scanning configuration and the external webhook/partial-failure drills.

## Delivered

- GitHub App installation-token exchange/cache and server-only runtime validation.
- Dedicated `content` branch and `content/` prefix enforcement with normalized safe paths.
- Blob-SHA optimistic concurrency and safe fixed commit metadata primitives.
- Signed webhook verification, replay-claim persistence, and trigger-only webhook handling.
- Git-tree reconciliation through the production Markdown renderer.
- PostgreSQL apply ledger/outbox schema and adapter for idempotent recovery.
- Unit/boundary coverage for traversal, unsafe writes, configuration, webhook/reconciliation behavior, and database boundaries.
- A `content_jobs` queue claimed with `FOR UPDATE SKIP LOCKED`, with leases, capped exponential backoff, attempt budgets, and dead-letter rows that are kept rather than deleted.
- Per-post ordering and burst collapsing enforced by partial unique indexes — one CLAIMED job per lock key, one PENDING job per dedupe key — so two workers racing produce a unique violation the loser retries rather than two interleaved handlers.
- A dedicated worker process built from the API workspace with `sync` and `scheduler` modes, each behind its advisory lock, waiting rather than exiting when another process holds it. HTTP API replicas run no timers.
- Lease recovery for a worker killed mid-job, plus a sweep that dead-letters a lapsed claim with no attempts left — otherwise that row is invisible to the claim query and never reports as failed.
- `POST /content/webhook`: verifies the signature over the unmodified request bytes, rejects a delivery with no id because replay cannot be detected without one, and enqueues a reconciliation carrying none of the payload. A redelivery answers `200` so the sender stops retrying.
- `/health/live` and `/health/ready` as separate questions. Only an unreachable database is `503`; an unconfigured, misconfigured, backlogged, or failing content pipeline reports itself at `200` with queue depth, age, dead count, and lapsed leases.
- The API boots and serves every public route with no content store configured, and reports a half-set configuration as misconfigured rather than as absent.
- Direct Git reconciliation now atomically creates the parent `Post` for a valid first translation, preserves all validated publication/frontmatter metadata, and rejects unknown taxonomy or media references rather than silently dropping them.
- An invalid update marks the existing translation `SYNC_FAILED` while retaining its last good render. A missing path marks it `MISSING_IN_GIT` while retaining that render; restoring a valid source returns it to `SYNCED`.
- Live GitHub App authentication, real bilingual branch reconciliation, replay idempotency, stale-SHA rejection, invalid-source recovery, missing-file recovery, and final healthy restoration were run on 2026-08-24. See [M3 live run](evidence/M3-live-run.md).
