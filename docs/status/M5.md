# M5 — Appearance and accessibility

Status: **Complete**
Snapshot: **2026-08-25**
Depends on: M4 shell/public read path  
Roadmap: [M5 definition and exit gate](../ROADMAP.md#m5--appearance-and-accessibility)

## Outcome so far

The server-resolved preference shell now consumes the locale-scoped owner allowlist from PostgreSQL through the strict public API, with an explicit legacy rollback source, bounded validated fallback, and a real localized HTTP `503` when no allowed value exists. The accessible settings UI, CSP pre-paint path, and reduced-motion wiring are present, and the THEMING §3 token vocabulary is adopted, enforced in CI, and passing a 26-pairing WCAG 2.2 AA matrix in both themes.

Font delivery and the browser half of the verification matrix are complete. The face set is reduced to what the design can select and every face carries a `unicode-range`; preloading is confined to two reviewed call sites; and the THEMING §9 list has a 35-test Playwright suite running in CI against a production build. On 2026-08-25, the owner visually approved the light theme and confirmed that the settings experience works with a screen reader, closing the two manual gates.

## Delivered

- Strict `portfolio_prefs` contract and allowlisted theme/font/size/motion registry.
- Cookie-resolved `data-theme`/`data-motion` attributes in the initial server response.
- Blog typography scoped to `.blog-reading-surface`.
- Reviewed nonced pre-paint path for `system` mode and public security headers.
- Accessible settings dialog for appearance, typography, motion, and language.
- Reduced-motion wiring across hero, particles, scramble text, typing text, smooth scroll, and related effects.
- Inline application styles removed.
- The THEMING §3 token vocabulary declared per theme, with `--color-success`, `--color-particle`, and `--color-scrim` as documented extensions; 106 colour utilities across 22 files migrated; every opacity-thinned text and border variant replaced with a measurable token.
- Five WCAG 2.2 AA failures the shared-value palette had hidden are fixed: muted text at 2.60:1 on light, Gold at 1.75:1, green at 2.28:1, red at 4.47:1 on dark, and the placeholder grey at 4.34:1 on dark.
- Three `dark:`-variant colour switches removed. No `@custom-variant dark` is declared, so they resolved against `prefers-color-scheme` rather than the selected `data-theme` — the tooltip rendered white on white for a dark-theme visitor on a light operating system, and the footer's social links went invisible on hover.
- The Skills category card no longer paints 60% of the foreground under foreground-coloured chips, which was 2.2:1 on dark and 3.3:1 on light.
- The two `prefers-color-scheme` fallbacks scoped `:not([data-system-theme])`, so the media fallback and the script-resolved attribute can no longer both apply.
- CI enforcement against raw colours, Tailwind palette utilities, retired token names, stale allowlist entries, and stylesheet/contract drift in either theme or either fallback copy.
- Strict public appearance contract and API projection for enabled themes, locale-compatible registry fonts, size steps, defaults, and the motion-toggle flag.
- Root layout appearance source selected by `PORTFOLIO_DATA_SOURCE=database|legacy`; the former hard-coded root settings singleton and dialog option arrays are removed.
- Appearance cache keys are resource/locale scoped and cookie independent; public API and rendered HTML responses do not send `Vary: Cookie`.
- Live first-response proof covers both locale defaults and a Persian visitor cookie whose valid light/reduced/XL choices are honored while an incompatible font is corrected to the configured Vazir default.
- Live rollback and fresh cold-outage runs prove the legacy source is API-independent and unavailable database data does not synthesize owner settings.
- A pre-stream production route gate now proves appearance cold/expired failures return localized secure HTTP `503`, while healthy and in-window validated pages remain `200` and explicit legacy mode never reads the API.
- The M4 `localStorage["theme"]` preference is now consumed once by the client: valid `light`, `dark`, or `system` values seed the versioned cookie only when no valid cookie exists, then the legacy key is removed. Malformed values are removed without affecting the server-resolved appearance.
- Article pages now emit the resolved `data-blog-font` and `data-blog-size` values on the reading surface in the server response. Project Markdown uses its own reading class, so a blog-only preference cannot affect portfolio content; the root/article allowlist lookup is request-deduplicated.
- `@portfolio/markdown` uses Shiki dual-theme output. Shiki 4 serializes light colours inline and exposes dark alternatives as custom properties; `globals.css` leaves light output intact and selectively overrides dark/system-dark output from `[data-theme]`. The code surface is painted by `--color-code-bg`/`--color-code-text`, so the pairing the contrast matrix measures is the pairing a reader sees.
- The 16 JetBrains Mono faces are reduced to the six the design can select: 400, 400 italic, 500, 600, 700, and 700 italic. `public/Fonts` is 7 files and 283 KB, down from 17 and 712 KB. Every face carries a `unicode-range`, and the Latin family declares no Arabic block.
- Font preloading is confined to two call sites — the root layout for the site font, the article route for a self-hosted blog family that is not already the site font — reading a static literal keyed by the registry key in `src/server/font-delivery.ts`. `test/font-delivery.spec.ts` fails if any other source file names a font file, if a declared face has no file or a file has no declaration, or if a `data-blog-*` selector appears outside `.blog-reading-surface`.
- A 35-test Playwright suite (`apps/web/e2e/`) discharges the browser half of THEMING §9 against `next build` + `next start`, with a fixture public API whose responses are parsed through the real contract schemas and whose article body is rendered by the real Markdown pipeline. It runs as its own CI job.
- Two defects the suite found are fixed: every Persian article route answered `404` because Next.js hands a non-ASCII `[slug]` through percent-encoded and the route validated it undecoded, and `pnpm lint` was failing on `dev` over the `localStorage` migration's `setState`-in-effect.
- Shiki 4 serializes its light code colours inline and exposes its dark alternatives as custom properties. The stylesheet now keeps light output intact and narrowly overrides the code surface and token colours only for selected dark/system-dark themes; the full production matrix proves dark, light, and a light-theme visitor on a dark operating system.
- The article shell is a token-backed translucent, blurred reading panel, so the selected theme remains atmospheric without competing with the title, metadata, navigation, or article text.
- Manual closeout: the owner reviewed the light theme and verified the screen-reader experience on 2026-08-25.

## Deliberately deferred

- **Binary font subsetting.** Every face declares a `unicode-range`, but the files are the upstream binaries. Vazir Code is a single dual-script file, so its range bounds when it is requested rather than what it contains. Splitting it needs re-encoding, which is a change to a vendored asset and belongs with M9's asset pipeline rather than here.
- **`style-src 'unsafe-inline'`.** Shiki writes per-token colours into `style` attributes, and `style-src-attr` is not supported widely enough to narrow the directive without losing code-block colour in Firefox. Removing it means converting Shiki's output to generated classes and shipping the generated CSS, which is a bigger change than the §8 line it satisfies.
- **One browser.** The matrix runs on Chromium. `unicode-range` and `@font-face` behaviour in Firefox and Safari is assumed.
