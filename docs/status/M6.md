# M6 — Authentication foundation

Status: **In progress**  
Snapshot: **2026-08-27**  
Depends on: M1  
Roadmap: [M6 definition and exit gate](../ROADMAP.md#m6--authentication-foundation)

## Outcome so far

The API authentication boundary is built and proven against a running system. All ten API_SPEC §5 endpoints answer, a two-factor login issues an opaque rotating session, passkey assertions are verified cryptographically with origin, RP ID, replay and counter enforcement, recovery works and sweeps other sessions, and every security event reaches an audit record that carries no credential.

Two surfaces remain: the authenticated admin shell, and the documented recovery/revocation drill. Both are the exit gate's remaining conditions.

## Delivered

- Opaque keyed session and CSRF token primitives, Argon2id hashing, hashed single-use recovery codes, single-use WebAuthn challenges, and cookie-mutation guards in [`packages/auth-core`](../../packages/auth-core).
- Explicit-apply owner provisioning gated by bootstrap file and expiry.
- **The API auth boundary** (`apps/api/src/modules/auth/`): CSRF rotation, password step, WebAuthn options/verify, passkey enrolment, recovery, session read, re-authentication, logout, session listing, and session revocation.
- **Full WebAuthn verification** through `@simplewebauthn/server`: origin and RP ID binding, single-use challenges, user-verification requirement, signature verification, and signature-counter regression handling with an owner notification.
- **Passkey enrolment** with `none` attestation, excluding already-registered credentials, authenticated and recent-auth gated. This is also the bootstrap answer: provisioning issues recovery codes, a code buys a session, and the first passkey is enrolled from that session.
- Progressive per-account and per-network throttling on login and, more strictly, on recovery.
- Session rotation at login and re-authentication, idle and absolute expiry, server-side revocation, and a session list that shows a coarse client label and never a token.
- **Deny-by-default authorization** (`authorization.ts`): an allowlist encoding API_SPEC §9, a recent-auth requirement on session-wide and destructive permissions, and an object-level ownership check.
- Structured audit events for every security-relevant action, written through a path that cannot turn a failed audit write into a failed refusal.
- A software WebAuthn authenticator (`apps/api/scripts/software-authenticator.ts`) so the passkey path is tested against real ES256 signatures rather than a stubbed verifier.
- 27 unit tests in [`apps/api/test/auth.spec.ts`](../../apps/api/test/auth.spec.ts) plus a committed live proof, `pnpm --filter @portfolio/api verify:auth`.

## Exit gate

| Exit condition                                                                                              | State                                                                               |
| ----------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| The admin shell cannot be reached without verified credentials                                              | **Open** — the boundary exists and refuses; there is no shell yet to put behind it  |
| Authentication, WebAuthn replay/origin, session, CSRF, recovery, role, and object-level negative tests pass | **Met** — 27 unit tests and 24 live checks                                          |
| An owner recovery and credential-revocation drill is documented and repeatable                              | **Open** — recovery and revocation both work; the drill is not written or rehearsed |

## The editor-permission decision is still owed

`EDITOR` is defined in the type system and its unambiguous permissions are recorded, but `isRoleAssignable()` refuses to grant it. API_SPEC §9's editor column still reads "configurable" and "no by default", and DECISIONS.md lists the v1 editor-permission matrix as an owner decision that is overdue. Encoding a guess would turn an open question into shipped behaviour nobody chose; deny-by-default already means every unlisted permission is refused, so the restriction costs nothing until the ADR lands. Provisioning stays owner-only in the meantime, exactly as that decision requires.
